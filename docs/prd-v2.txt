0. EXECUTIVE DECISION
============================================================

PRODUCT:
Agent Undo

ONE-LINE:
“Ctrl+Z for AI agents.”

CORE PROMISE:
An AI coding agent can make a mess. Agent Undo lets the developer safely restore
the state that existed before the agent session.

PRIMARY INITIAL USER:
Developers using AI coding agents locally, especially Claude Code, Cursor,
Codex-style agents, terminal agents, and other tools that can modify a repo.

MVP:
Local-first checkpoint + session log + restore mechanism around an agent run.

DO NOT build first:
- enterprise dashboard
- cloud control plane
- complex RBAC
- giant policy engine
- generic “AI governance” platform
- 50 integrations
- browser UI
- distributed tracing platform
- fancy AI analysis

The first product must be understandable in one sentence and demonstrable
in under 30 seconds.

THE VIRAL ARTIFACT:
GitHub repo + README + terminal UX + catastrophic demo.

THE BUSINESS WEDGE:
Rollback first.
Observability second.
Permissions third.
Governance fourth.

LONG-TERM CATEGORY:
Infrastructure for safe autonomous software agents.

============================================================
1. WHY THIS PRODUCT EXISTS
============================================================

The world is moving from:

AI writes code

to:

AI changes systems.

Once an agent can:
- edit dozens of files
- run shell commands
- install dependencies
- alter configuration
- modify git state
- call external services
- execute migrations
- manipulate environments

the developer gets a new problem:

“What exactly did the agent do, and can I safely undo it?”

Traditional version control is not always enough because:
- not every change is committed
- generated files may be ignored
- package installations alter local state
- scripts can create/delete files
- environment state can change
- commands can have side effects
- developers may want to compare a whole session, not one commit

Agent Undo exists to create a simple safety primitive around agent execution.

MENTAL MODEL:

BEFORE AGENT
      |
      v
[CHECKPOINT]
      |
      v
[AGENT DOES THINGS]
      |
      v
[SESSION RECEIPT]
      |
      +------ KEEP ------> current state
      |
      +------ INSPECT ---> session diff
      |
      +------ UNDO ------> restore checkpoint

============================================================
2. PRODUCT THESIS
============================================================

The thesis:

AI agents increase software creation speed.
Speed increases the amount of risky state changes.
Therefore developers need a reversible execution layer.

The emotional proposition:
“I want to let my agent run without being terrified of what happens.”

The technical proposition:
“Capture enough pre-run state to make agent execution reversible.”

The business proposition:
“Every agent action can eventually become observable, attributable,
policy-controlled, and reversible.”

============================================================

MVP SUCCESS CRITERIA:

A developer can:

A. start a protected agent session
B. allow the agent to modify the repo
C. inspect what happened
D. undo the session
E. return the project to the pre-session filesystem/git state

MVP MUST HANDLE:
- modified files
- newly created files
- deleted files
- renamed/moved files
- git tracked/untracked distinctions
- ignored files where safely possible
- basic metadata needed to reconstruct state

- restore failure reporting

MVP SHOULD HANDLE:
- package metadata changes
- shell command logging
- process lifecycle logging
- session IDs
- human-readable session summaries

MVP MAY DEFER:
- database side effects
- remote infrastructure changes
- network mutation rollback
- cloud resources
- browser state
- external SaaS side effects

IMPORTANT:
Do not falsely advertise that the MVP can undo arbitrary external side effects.

POSITIONING:

“Undo the entire universe.”

============================================================
8. TECHNICAL PRINCIPLES
============================================================

PRINCIPLE 1:
Local-first.

No account.
No cloud dependency.
No network required for core functionality.

PRINCIPLE 2:
Safety over cleverness.

Never claim a restore succeeded when verification is incomplete.

PRINCIPLE 3:
Fail closed when correctness is uncertain.

PRINCIPLE 4:
Never destroy the original state before a verified backup/checkpoint exists.

PRINCIPLE 5:
Every mutation must be auditable.

PRINCIPLE 6:
Restore must be idempotent where practical.

PRINCIPLE 7:
The user must always understand:
- what is being captured
- where it is stored
- what can be restored
- what cannot be restored

PRINCIPLE 8:
The happy path should require almost no configuration.

RECOMMENDED INITIAL STACK:

Use Go for the Agent Undo core and CLI. This is an explicit architecture decision,

Why Go:
- filesystem-heavy workload

- concurrency and cancellation
- cross-platform compilation
- single-binary distribution
- minimal runtime dependencies
- strong standard library for filesystem/process primitives
- predictable failure handling for safety-sensitive code

TypeScript is reserved for future web/dashboard/SDK surfaces. Do not introduce

CLI:
Command-based CLI.

Go package principles:
- keep public APIs small
- prefer standard library first

- do not leak CLI/UI concerns into checkpoint/restore packages

============================================================
10. CHECKPOINT DESIGN
============================================================

GOAL:
Create a reliable representation of the state BEFORE the agent begins.

Checkpoint should capture:

- repository root
- git HEAD
- git status
- tracked files
- untracked files
- ignored files if configured to capture
- file contents or content-addressed snapshots
- file metadata necessary for restore
- manifest version
- timestamp
- session ID

PREFERRED MODEL:
Content-addressed object store.

Conceptual:

~/.agent-undo/
  objects/
  sessions/
  manifests/
  locks/

Repository-local metadata can optionally live under:
.git/agent-undo/

Do not pollute the repo with huge files unless explicitly configured.

MANIFEST EXAMPLE:

{
  "schemaVersion": 1,
  "sessionId": "...",
  "repoRoot": "...",
  "createdAt": "...",
  "gitHead": "...",
  "files": [
    {
      "path": "src/app.ts",
      "sha256": "...",
      "mode": "100644",
      "size": 1234
    }
  ]
}

============================================================
11. RESTORE ENGINE
============================================================

Restore algorithm:

1. Acquire repository lock.
2. Load checkpoint manifest.
3. Validate current repository location.
4. Detect current state.
5. Compute desired pre-session state.
6. Show restore plan if interactive.
7. Preserve current post-agent state in an emergency recovery checkpoint.
8. Restore original files.
9. Remove files created after checkpoint where ownership can be established.
10. Restore deleted files.
11. Handle renames through content/path reconciliation.
12. Recompute state.
13. Verify against checkpoint.
14. Release lock.
15. Emit success/failure summary.

CRITICAL:
Before executing destructive restore:
create a POST-STATE recovery checkpoint.

This means:
undo itself can be undone.

That is a killer product property.

JOKE / BRAND MOMENT:

“Undo has an undo.”

Potential terminal line:

✓ pre-agent state restored
✓ your regret has been archived

============================================================
12. SAFETY RULES
============================================================

Every restore operation must:
- use explicit paths
- prevent path traversal
- never write outside repository scope without explicit opt-in
- avoid following unsafe symlinks
- detect symlink behavior
- protect checkpoint integrity
- use atomic writes where possible
- maintain locks to prevent concurrent destructive operations

NEVER:
- rm -rf arbitrary paths
- trust agent-provided restore paths
- overwrite without checkpoint verification
- silently ignore failed restores
- claim “100% reversible” for external side effects

18. TEST STRATEGY
============================================================

Test categories:

UNIT TESTS
- manifest encoding/decoding
- hashing
- snapshot creation
- diff calculation
- path validation
- event serialization

INTEGRATION TESTS
- modify file -> restore
- create file -> restore
- delete file -> restore
- rename file -> restore
- many files -> restore
- untracked files -> restore
- ignored files -> restore
- interrupted process -> recover
- concurrent run -> blocked safely

PROPERTY TESTS
For supported filesystem state:

restore(checkpoint(state)) => state

More formally:

state_after_restore ≈ state_before

with explicit exceptions documented.

CHAOS TESTS:
- process killed during checkpoint
- process killed during restore
- disk nearly full
- permission denied
- file locked
- symlink attack attempt
- malformed manifest
- corrupted checkpoint
- concurrent sessions

============================================================
19. DEFINITION OF DONE FOR MVP
============================================================

MVP is DONE only when:

1. A clean repo can be checkpointed.
2. 20+ files can be changed by an agent/process.
3. Agent Undo can show the session summary.
4. Restore returns the repo to pre-session state.
5. Verification can prove the restore.
6. Restore failure is explicit.
7. Recovery checkpoint exists.
8. Tests cover destructive edge cases.
9. README setup works from a clean machine.
10. A first-time developer can understand the repo in <2 minutes.
11. A demo can be recorded in <30 seconds.
12. No network account is necessary.

49. CURSOR IMPLEMENTATION BRIEF
============================================================

PASTE THIS INTO CURSOR AS THE MASTER ENGINEERING PROMPT:

You are the staff/principal engineer leading the implementation of Agent Undo.
Act with the engineering standards of a mature Silicon Valley developer-tools
company, but keep the product ruthlessly small for MVP.

PRODUCT:
Agent Undo

POSITIONING:
Ctrl+Z for AI agents.

MISSION:
Build a local-first safety layer that checkpoints a developer workspace before
an AI agent session, records what happened, and can safely restore supported local
workspace state to the pre-session state.

NON-NEGOTIABLE LANGUAGE DECISION:
Use Go for the core and CLI. Do not introduce Node.js/TypeScript into the core
runtime. TypeScript may be used later for a web/dashboard/SDK surface.

ENGINEERING PRIORITIES, IN ORDER:
1. Data safety
2. Restore correctness
3. Verification
4. Crash/interruption recovery
5. Security boundaries
6. Simple architecture
7. CLI UX
8. Performance
9. Extensibility

MVP BOUNDARY:
Support reversible local repository/workspace state. Do not pretend to reverse
external side effects such as production databases, cloud APIs, emails, purchases,
or remote infrastructure.

ARCHITECTURE:
Use idiomatic Go with:
- cmd/agent-undo/main.go
- internal/checkpoint
- internal/restore
- internal/diff
- internal/session
- internal/manifest
- internal/storage
- internal/process
- internal/security
- internal/verify
- internal/ui
- adapters/git
- adapters/filesystem
- adapters/shell
- adapters/agents

DESIGN RULES:
- standard library first
- minimize third-party dependencies
- keep destructive operations isolated
- no global mutable state
- context.Context for cancellation
- typed, inspectable data structures
- explicit errors
- deterministic core logic
- atomic writes wherever practical
- repository/path boundaries enforced centrally
- checkpoint data integrity verified

CRITICAL SAFETY CONTRACT:
Agent Undo must never perform destructive restore without first preserving the
current post-agent state in a recovery checkpoint.

Restore must follow:
LOCK -> LOAD -> VALIDATE -> PLAN -> RECOVERY CHECKPOINT -> APPLY -> VERIFY -> REPORT

“Success” may only be printed after verification.

SECURITY REQUIREMENTS:
Treat path traversal, symlinks, permissions, malformed manifests, corrupted
checkpoints, concurrent access, and interrupted writes as hostile/failure cases.
Never trust agent-provided paths. Never write outside the repository boundary
without an explicit, separately reviewed feature.

TESTING REQUIREMENTS:
Every risky filesystem feature requires:
- unit tests
- integration tests
- failure-path tests
- interruption tests where relevant
- fuzz tests for path/manifest parsing where relevant
- race-enabled CI

BEFORE CODING:
1. Inspect the existing repository.
2. Determine what already exists; do not invent duplicate abstractions.
3. Produce a short architecture note.
4. Identify the exact files to change.
5. List the dangerous operations and their mitigations.
6. Define tests before implementation.

IMPLEMENTATION LOOP:
1. Make the smallest coherent change.
2. Add/update tests.
3. Run gofmt.
4. Run go test ./...
5. Run go test -race ./... when applicable.
6. Run go vet and configured static analysis.
7. Exercise the failure path.
8. Review the diff for unrelated changes.

DO NOT:
- rewrite unrelated code
- add speculative abstractions
- add cloud services
- add dashboards
- add billing
- add enterprise RBAC
- implement external-side-effect rollback
- hide failures for a nicer demo
- claim guarantees the implementation cannot prove

CLI UX PRINCIPLES:

agent-undo undo ...
agent-undo verify ...

The user should always understand:

- whether verification succeeded
